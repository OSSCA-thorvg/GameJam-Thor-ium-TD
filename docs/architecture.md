# Thor-ium TD 아키텍처 제안

갱신일: 2026-11-03. 사용자가 승인한 엔진·Rubiks 조사와 최신 설계 원칙을 반영했습니다. 아래 타입·디렉터리·타깃은 설계 제안이며 게임 구현이나 의존성 도입 결과가 아닙니다. [시작 계획](preproduction-plan.md), [규칙 선택지](rule-options.md), [조사 근거](architecture-research.md)를 함께 확인합니다.

## 설계 기준

2026-11-04 첫 구현 승인을 받아 SDL·ThorVG 시연판을 만들었습니다. 이 문서의 상세 설계 제안과 실제 구현 범위를 구분하며, 현재 파일·빌드·검증 상태는 [첫 구현 기록](implementation-v0.1.md)을 기준으로 확인합니다.

[큰 구조·폴더 배치 비교](architecture-overview.md)의 최신 수정안을 기준으로 엔진·게임·앱·플랫폼을 구분합니다. 사용자는 폴더 B의 실행 경계 + 기능별 구성을 선택했고, 규칙과 표현을 분리해도 엔진 기반은 별도로 드러내도록 요청했습니다. 상세 타입·타깃은 계속 검토합니다.

**범용 엔진을 만드는 구조와 Thor-ium TD를 깔끔하게 만드는 구조는 같지 않습니다.** 현재 게임의 상태·수명·변경 이유·테스트를 설명하는 경계부터 둡니다. 이름이 비슷한 GameObject·Actor·Node를 구현하는 것이 목표가 아닙니다.

- 게임 규칙은 렌더러·브라우저 없이 실행·검증할 수 있어야 합니다.
- 한 판의 상태 소유자와 여러 기능을 함께 바꾸는 순서가 명확해야 합니다.
- 지상·지하 화면을 바꿔도 판의 상태가 남고 새 판에서는 초기화돼야 합니다.
- 적 외형·카드 수치 변경이 전투 코드·ABI 전체의 변경을 요구하지 않아야 합니다.
- 새로운 추상화는 현재 격리할 책임이나 실제 변경·테스트 요구로 설명합니다.

인터페이스가 한 구현뿐이라는 이유만으로 무가치하지는 않습니다. 반대로 미래 교체 가능성만으로 포트·팩토리·관리자를 늘리지 않습니다.

## 전체 책임과 의존 방향

2026-11-04 SDL 반영 요청의 최신 큰 그림은 [SDL·공통 UI 구조도](cross-platform-ui-proposal.md)의 주요 코드 의존과 입력→화면 흐름을 따릅니다. 아래 일반 경계에서 엔진의 UI/Input·Graphics와 SDL 플랫폼 어댑터를 구체화한 안입니다. 게임 전용 손패·정비창은 게임 표현에, 일반 UI 도구는 엔진에 둡니다.

추천 실행 구성은 C++17·Meson·Emscripten 기반 규칙과 ThorVG를 WASM으로 연결하고 TypeScript 웹 셸이 로딩·입력·HUD를 담당하는 방식입니다. Rubiks에서 원리를 참고하며 정확한 도구·ThorVG 버전은 첫 구현 범위에서 확인합니다.

~~~mermaid
flowchart TD
    web[웹·WASM 어댑터] --> app[App: 수명·실행 조합]
    app --> session[Game rules: 판 상태·기능 규칙]
    app --> presentation[Game presentation: 두 뷰·공개 표시 정보]
    app --> engine[Engine: 렌더·에셋·변환·시간 도구]
    presentation -->|공개 정보 계약| session
    presentation --> engine
~~~

이 그림은 소스 의존 방향입니다. 실행 중 공개 상태·결과는 코어에서 표현으로 전달되지만 코어가 표현을 호출하거나 include하는 것은 아닙니다. 엔진은 게임을 참조하지 않고, 게임 규칙은 ThorVG·Emscripten·웹·파일 파서에 의존하지 않습니다. 자세한 실행 흐름과 엔진의 범위는 [큰 구조 수정안](architecture-overview.md)을 따릅니다.

## 앱·판·개체의 수명

| 수명 | 소유자와 내용 | 종료·변경 시 정책 |
| --- | --- | --- |
| 앱 | ClientApp: 콘텐츠·에셋 저장소·렌더러·세션·경계 연결 | 입력·루프 정지 후 세션과 렌더 자원 정리, ThorVG 종료 |
| 콘텐츠 | 앱이 보유한 검증 카탈로그 | 실행 중인 판에서는 고정, 변경은 새 판·새 실험에 반영 |
| 판 | GameSession이 RunState 소유 | 종료 뒤 결과 표시 가능, 새 판은 새 RunId로 상태 재생성 |
| 기능 상태 | 지상·지하·덱·재료·도구·성장·공세 예약 | 뷰 전환으로 제거하지 않음 |
| 개체 | 지상 상태의 적·타워·유닛·탄환 배열 | 안정적 ID로 참조, 정한 단계에서 제거 |
| 표현 | 렌더러의 도형·Lottie 인스턴스·연출 상태 | 개체 제거·새 판에 맞춰 정리, 규칙상 보상을 생성하지 않음 |

GameSession은 소유자와 조정자입니다. 카드별 효과·레시피·이동의 모든 분기를 담는 거대 클래스로 만들지 않습니다. 여러 상태를 바꾸는 카드 사용·제작·정산은 기능별 처리 함수가 검사와 적용을 조합합니다.

타이틀→플레이→결과는 앱 화면 수명이고, 플레이 중 전투→정비는 판의 단계입니다. 지상·지하 뷰 전환을 두 월드의 파괴·재생성으로 처리하지 않습니다. 이를 위해 범용 SceneManager나 IWorld 베이스가 필요한 것은 아닙니다.

## 탑다운 지상과 단면 지하의 좌표

지상 탑다운·지하 단면을 전투·정비 단계에 따라 전환하는 Q-22=A를 사용자 선택으로 확정했습니다. 두 뷰는 각 좌표·입력 변환을 갖고 같은 판의 상태를 사용합니다.

| 개념 타입 | 의미·단위 제안 | 사용 위치 |
| --- | --- | --- |
| SurfacePoint | 평면 x·y, 논리 타일 단위 실수 | 경로 이동·사거리·탄환 |
| SurfaceCell | 지상 열·행 정수 | 경로·설치 지점·유닛 배치 칸 |
| MineCell | 수평 열·지층 깊이 정수 | 4방향 갱도·굴착·8이웃 단서 |
| ScreenPoint | 캔버스 drawing-buffer 픽셀 | 포인터·미리보기·렌더링 |
| ViewTransform | 해당 뷰의 이동·배율·viewport | 논리→화면 및 입력 역변환 |

웹은 CSS 좌표를 drawing-buffer 좌표로 한 번 변환합니다. 표현 계층이 활성 뷰의 변환으로 논리 대상을 구합니다. 변환에 적용한 화면 크기·DPR·카메라 상태가 드롭 판정과 일치해야 합니다. 리사이즈·뷰 전환 중 드래그는 취소하는 첫 정책을 제안합니다.

지상의 평면 y와 지하의 깊이는 다른 의미입니다. 공통 Vec2라는 이유로 섞어 전달하지 않습니다. 카메라·그림자·지층 옆면은 표현이고 피해·저지·굴착 접근은 논리 좌표에서 계산합니다.

첫 뷰는 고정 카메라와 화면 맞춤부터 비교합니다. 자유 줌·회전·3D picking은 필요성이 확인되면 추가합니다. 카메라 밖 개체의 표현을 생략하는 것과 게임 갱신 중단은 다른 정책입니다.

## 맵·설치·이동의 현재 규칙과 후속 전환

Q-01=A·Q-04=A·Q-08=A를 반영합니다. 지상 확장은 정해진 웨이브 뒤 선택하며 첫 3웨이브 검증은 2웨이브 뒤 1회입니다. 첫 전장은 고정 적 경로·건물 패드·유닛 배치 칸을 사용하고 광부는 열린 갱도를 상하좌우로 자동 이동합니다. 숫자는 최초 둥지 배치의 주변 8칸 수로 고정합니다.

사용자는 첫 검증을 A로 시작하되 나중에 B인 자유 배치·경로 재계산과 지하 중력·사다리로 전환할 수 있기를 요청했습니다. 아래는 그 요구를 위한 책임 분리 제안입니다. 후속 실행 기능을 지금 구현하는 목록은 아닙니다.

| 책임 | 첫 검증 A | 후속 B에서 확장할 부분 | 유지할 경계 |
| --- | --- | --- | --- |
| 지상 지형·점유 | 고정 도로·건물 패드·유닛 배치 칸, 배치된 개체 위치·점유 | 배치 후보 영역과 건물 크기·점유에 따른 통행 조건 | 콘텐츠 지형과 런타임 점유를 구분 |
| 설치 검사 | 카드 종류별 허용 칸·점유·에너지·슬롯 검사 | 자유 배치 후보와 모든 필수 경로의 연결 검사 | 대상·비용 검사 결과를 명령 처리에 반환 |

| 지하 숫자 | 최초 둥지 배치의 8이웃 수, 공개 여부·처리 여부 별도 | 이동 방식 변경과 무관하게 동일한 단서 의미 유지 | 이동용 이웃과 단서용 이웃을 별도 함수·테스트로 관리 |

### 첫 구조에 둘 값과 호출 경계

아래 이름은 타입 있는 값의 개념안입니다. 빈 클래스나 라이브러리를 미리 만들라는 의미가 아닙니다.

| 값·처리 | 책임 제안 |
| --- | --- |
| SurfaceMapDefinition | 도로·배치 허용 구역·진입점·거점·사전 정의 경로 |
| SurfaceOccupancy | 건물·유닛의 실제 점유 위치와 개체 ID, 적 통행·저지 의미는 구분 |
| PlacementValidation | 배치 대상·종류별 적합성·실패 이유, 성공 전 자원·점유 변경 없음 |
| SurfaceRoute | 적이 따라갈 논리 경로와 식별자, 현재 위치·HP는 EnemyState 소유 |
| MineBoardDefinition | 지층·광물·등급·최초 둥지 배치, 판 진행 중 단서 기준으로 유지 |
| MineBoardState | 공개·굴착·둥지 처리 상태, 최초 둥지 배치와 별도 |
| MineRoute | 광부의 현재 위치에서 유효한 작업 위치까지의 경로, 도착 후 굴착 시작 |

카드·HUD·렌더러에 특정 건물 패드의 배열 인덱스를 설치 규칙으로 넣지 않습니다. 입력은 논리 위치를 제시하고 설치 규칙이 허용 여부를 판단합니다. 첫 구현의 패드와 칸도 같은 위치·점유 데이터로 표현하는 안입니다. 건물과 유닛의 배치·적 통행 규칙은 구분하고 유닛 저지를 단순한 길막 점유로 처리하지 않습니다.

광부 경로는 이미 열린 칸만 통과합니다. 미굴착 목표 칸은 도달 가능한 열린 작업 칸과 상하좌우로 맞닿아야 하는 안입니다. 대각선으로만 닿은 타일·연결되지 않은 갱도·도구 등급 부족은 작업·재료 소모 전에 거절합니다. 수직 이동의 사다리 연출을 쓰더라도 첫 규칙에서는 사다리 아이템·중력·낙하 피해를 요구하지 않습니다.

보드 초기화 때 최초 둥지 배치로 8이웃 숫자를 계산하거나 검증합니다. 열린 둥지·처리 완료 둥지도 최초 배치에는 남기고 숫자를 다시 세지 않습니다. 숫자는 현재 남은 위험 수와 구분해 안내합니다. HUD에는 공개된 칸의 숫자·표식만 전달하며 미공개 둥지 배열은 보내지 않습니다. 스캔은 접근 가능한 경계 1칸의 광물·둥지·숫자 공개로 정했습니다. 실제 굴착 후 숫자 0은 연결 영역과 경계 숫자의 정보 공개로 구분하며 실제 둥지 굴착에서만 다음 웨이브 추가 적을 한 번 예약·예고합니다.

### 확장 적용과 후속 기능의 전환 순서

첫 지상 확장도 후보 검증 후 한 번 적용합니다. 새 진입점에서 거점으로 가는 경로, 기존 건물·유닛의 위치·HP·슬롯 유지, 미리보기와 실제 배치의 일치를 확인하는 안입니다. 판의 단계가 정비이고 2웨이브 완료 조건을 충족했는지 검사하며 화면 재진입이나 같은 선택의 재처리가 중복 확장·보상을 만들지 않아야 합니다. 전격탑 등 실제 보상은 별도로 선택한 정책을 따릅니다.

후속 자유 배치는 먼저 점유 변경 후보에서 필요한 경로가 모두 유지되는지 검사한 뒤 점유·경로·카드·에너지 변경을 함께 적용하는 방식으로 확장합니다. 길이 막히거나 진행 중인 적을 유효 경로에 연결할 수 없다면 상태를 보존하고 거절하는 후보입니다. 새 경로를 적용할 때 적의 ID·현재 위치·HP를 유지하고 저지 관계는 새 배치에 맞게 검증해야 합니다. 길막 허용 여부와 경로 알고리즘·정책은 B를 실제 구현할 때 결정합니다.

후속 지하 중력·사다리는 이동 가능 연결과 작업 위치 검사를 먼저 확장합니다. 지지면·사다리 설치·이동 중 갱도 변경에 대한 테스트를 추가하고, 굴착 완료 시 한 번만 재료·작업을 반영하는 경계는 유지합니다. 지상 자유 배치와 지하 이동 확장은 각각 도입·검증할 수 있으며 한 번에 바꿀 필요는 없습니다.

지금은 고정 경로 조회와 4방향 경로 처리에 필요한 함수·데이터만 둡니다. B를 위해 범용 내비게이션 서비스·물리 엔진·교체 가능한 모든 규칙의 인터페이스를 미리 만들지 않습니다. 이 제안은 D-30의 현재 요구와 변경 비용을 기준으로 검토합니다.

## 데스크톱·모바일 입력과 화면 경계

Q-07의 선택은 데스크톱 60 FPS 우선과 모바일 UI·UX 준비입니다. 손패·HUD·정비 패널은 화면 폭에 맞춰 배치하고 카드 탭→대상 탭과 드래그가 같은 카드 사용 명령을 만들도록 제안합니다. 작은 화면의 구체 배치는 [UI·UX 계획](interface-plan.md)을 따릅니다.

웹 입력 어댑터는 포인터 식별자·선택·드래그 상태를 소유하고 화면 좌표를 해당 뷰의 논리 좌표로 변환합니다. 취소·뷰 전환·리사이즈 때 미확정 동작을 해제하고 게임 명령을 보내지 않습니다. CSS 크기·출력 버퍼 크기·DPR을 중복 적용하지 않으며 게임 코어는 터치 여부나 휴대전화 모델을 알 필요가 없습니다. UI가 차지한 영역을 뺀 실제 캔버스 영역으로 카메라·입력 변환을 함께 갱신합니다.

렌더 목표 60 FPS와 고정 시뮬레이션 tick은 별개입니다. 기기별 출력 해상도·효과·Lottie 갱신 품질을 조정하더라도 피해·보상·굴착 규칙은 유지하는 방향이며 실제 기준은 측정 뒤 정합니다. 모바일 화면을 준비하는 것과 실제 기기에서 성능을 확인하는 것은 각각 기록합니다.

## 상태 데이터와 기능 조합

EnemyDefinition은 최대 체력·속도·거점 피해·지원 능력·에셋 키를 참조합니다. EnemyState는 정의 ID·현재 체력·위치·쿨다운·저지 관계를 보유합니다. TowerState·UnitState·ProjectileState도 필요한 값으로 시작합니다. 클래스마다 공통 Transform·Update·이벤트 구독을 강제하지 않습니다.

참조는 배열 주소나 손패 인덱스 대신 RunId·EntityId·CardInstanceId를 사용합니다. 첫 구현에서는 판 안에서 ID를 재사용하지 않는 단순한 발급 정책을 후보로 둡니다. 저장 공간 재배치와 ID는 분리하고 더 복잡한 핸들·세대 체계는 필요할 때 검토합니다.

지원 능력은 정의를 로딩할 때 타입과 매개변수를 검증하고 전투 함수에 연결합니다. 새로운 능력에는 새 규칙과 테스트가 필요합니다. 미래 유저 몬스터만을 위해 임의의 Component 조합·행동 그래프·플러그인 체계를 만들지 않습니다.

Q-19=B에 따라 같은 CardInstanceId가 여러 UnitState를 소환할 수 있습니다. 소환마다 새 EntityId를 발급하고 카드의 사용 가능성·에너지·배치 대상·전장 전체 슬롯을 검사합니다. 카드 출처 기록은 추적용이며 살아 있는 개체가 같은 카드를 독점하는 잠금으로 사용하지 않습니다. 첫 유닛은 1명당 1슬롯이고 새 판의 기본 상한은 6입니다. 플레이 중 상한 업그레이드를 지원하며 강화 조건·비용·최종 상한은 미정입니다.

슬롯은 살아 있는 아군의 전장 자원으로 관리하고 카드 장수에서 계산하지 않습니다. RunState에서 상한과 사용량을 구분합니다. 정비·다음 웨이브에서도 생존 UnitState의 ID·위치·현재 HP·점유 슬롯을 유지하고 전환만으로 전원 제거하거나 체력을 초기화하지 않습니다. 슬롯은 사망이나 실제 제거에서 반환하며 정비 진입 자체로 반환하지 않습니다.

지정 위치 자동 교전·저지는 확정이고 전투 시간은 정비 중 멈춥니다. 정비에서는 무료 재배치가 가능하며 대상·새 배치 칸을 검증한 뒤 같은 UnitState의 위치만 바꿉니다. 재배치 UI에서 지상 뷰를 열어도 게임 단계는 정비로 유지해 전투·에너지 회복을 재개하지 않습니다. 현재 HP·EntityId·점유 슬롯을 보존하고 실패하면 원래 위치도 유지합니다. 자리 교환·겹침·퇴각은 미정입니다.

슬롯 강화는 금 같은 재화 광물을 소비합니다. 정비 단계·금 잔액·선행 조건·상한을 검사한 뒤 금 소비와 상한 변경을 함께 적용하는 후보입니다. 기존 유닛·HP를 재생성하지 않으며 가격·강화 단계·최종 상한은 미정입니다.

치료는 정비 중 재료를 써 선택한 유닛에 적용합니다. 재료·회복량·횟수는 미정이며 금을 치료 비용으로 통일한 것은 아닙니다. 생존 대상·부족 HP·재료를 검사하고 소비와 HP 증가를 한 번 반영하며 최대 HP를 넘지 않게 합니다.

최대 체력 강화가 자동 치료나 새 EntityId 생성을 유발하지 않게 현재 HP 보존안을 추천합니다. 새 판에서는 기존 성장 초기화 방향에 맞춰 유닛·점유 슬롯·금 잔액·슬롯 강화를 정리하고 기본 6슬롯으로 시작하는 기준안입니다.

## 명령·결과와 변경 경로

명령 예시는 카드 사용·교환·굴착·스캔·표식·제작·슬롯 강화·선택 치료·정비 재배치·보상 교체·확장·다음 공세 시작입니다. 금 모집은 유효한 유닛 카드 후보 3개와 선택한 1개의 획득 결과로 처리합니다. 필드 UnitState 생성·전투 에너지 사용·슬롯 점유는 실제 카드 사용 명령에서만 처리합니다. 명령은 타입이 있는 값으로 전달하고 단계·대상·자원·상한을 검사한 뒤 상태를 변경합니다.

~~~mermaid
sequenceDiagram
    participant UI as 입력·HUD
    participant App as 앱 경계
    participant Game as GameSession
    participant Rule as 기능 규칙
    participant View as 표현·음향
    UI->>App: 카드 ID와 대상 의도
    App->>Game: 타입 있는 명령
    Game->>Rule: 단계·대상·비용 검사
    Rule-->>Game: 거절 이유 또는 적용 결과
    Game->>Game: 유효한 변경을 한 번 반영
    Game-->>View: 공개 상태와 확정 결과
    Game-->>UI: 명령 결과
~~~

핵심 보상·제작을 전역 이벤트 구독 순서로 결정하지 않습니다. 채굴 모듈이 웨이브를 직접 부르지 않고 완료 결과를 세션이 재료·공세 예약에 반영합니다. 음향·VFX가 EnemyKilled·DigCompleted를 여러 번 조회해도 보상이 다시 발생하지 않아야 합니다.

정비는 해당 구간의 확장·고정 보상을 먼저 처리한 뒤 채굴·제작·금 모집·덱 편집·치료·재배치를 오가고 마지막에 준비 완료하는 흐름을 제안합니다. 새 금을 얻어 모집한 뒤에도 덱 반영이 가능해야 합니다. Q-20에서 1대1 교체·활성 8장 유지와 정비 후 손패 재구성·최근 획득 1장 우선을 선택했습니다. 코일은 제작 시 활성 덱 전격탑 조건을 검사하는 후보입니다.

### 덱 교체와 손패 재구성

첫 검증은 기본 8장·손패 4장이고 도감 UI는 후속입니다. 획득은 기존 1장과 새 1장을 교체합니다. 새 카드에는 새 CardInstanceId를 주고 기존 필드 병력·건물은 덱 교체만으로 재생성하지 않는 안입니다. 개체는 콘텐츠 정의를 참조하고 제거한 카드 객체의 주소에 의존하지 않습니다.

정비 완료 때 현재 활성 8장으로 손패 4장·대기열 4장을 구성합니다. 최근 획득 우선은 종류가 아닌 실제 CardInstanceId로 처리하며 중복 배치하지 않습니다. 여러 획득 중 활성 덱에 남은 최신 카드를 찾고 없으면 일반 구성하는 안입니다. [플레이 사양 P-02](first-playable-spec.md)는 판 전체 획득 이력에서 활성 덱의 최신 인스턴스를 우선하고 부족한 행동 분류·나머지를 활성 순서로 채우는 추천안을 구체화합니다. 아직 채택 전이며 첫 고정 손패·일반 사용·교환 순서도 같은 문서를 기준으로 검토합니다.

재구성은 준비 완료의 단계 전환에서 한 번 적용하고 UI 열기·렌더 호출로 반복하지 않습니다. 전환 때 드래그를 취소하고 이전 웨이브·단계의 카드 명령을 거절하는 안입니다. 잘못된 준비 완료가 손패나 난수를 미리 바꾸지 않는지 검증합니다.

## 시간과 갱신 순서

브라우저 프레임 시간과 고정 게임 tick을 분리합니다. 전투·정비 분리와 정비당 5굴착·추리 시간 제한 없음은 Q-03=A로 확정했습니다. 60Hz는 첫 후보이며 목표 환경과 테스트로 30/60Hz를 비교할 수 있습니다. catch-up 상한과 누적 시간 처리도 함께 정하고 탭 숨김·pause 복귀 시 긴 부재 시간을 공세로 따라잡지 않는 정책을 제안합니다.

- 전투: 적·타워·유닛·탄환·에너지·공세 시간 진행.
- 정비의 광부 동작: 광부 작업 시간만 진행, 전투 시간·에너지는 정지.
- 메뉴·선택: 의도 명령을 처리하고 해당 판의 시뮬레이션을 멈춤.
- 표현: 게임 상태와 애니메이션 시간에서 외형 구성, 규칙 완료를 Lottie 콜백에 맡기지 않음.

웨이브 완료는 예정된 적이 모두 등장했고 생존 적이 없는지를 기준으로 판단합니다. 생존 아군은 정비와 다음 웨이브에 남는 상태이며 완료를 막는 잔여 적 수에 포함하지 않습니다. 정산에서 아군·현재 HP·사용 슬롯을 초기화하지 않습니다.

다음은 사용자가 가격처럼 일일이 선택할 필요 없이 검토할 수 있는 **기술 가정**입니다. 아직 구현된 규칙은 아닙니다.

1. 입력 명령은 수신 순서대로 매번 다시 검증합니다.
2. 전투 tick은 공세 생성→이동·저지→공격·피해→사망·관계 정리→거점 도달→승패·웨이브 정산 순서를 후보로 둡니다.
3. 같은 tick에 공격으로 사망한 적은 거점 피해를 주지 않고 거점 체력 0과 마지막 적 정리가 겹치면 패배를 우선하는 후보입니다.
4. 표적 우선순위가 같으면 안정적인 ID 등으로 동률을 해소합니다.
5. 제거·재시작 뒤 오래된 표적·저지·드래그 ID는 거절합니다.

이 순서는 명시적 함수 호출로 표현하고 범용 tick 그래프나 병렬 작업 스케줄러를 먼저 도입하지 않습니다. 같은 빌드·콘텐츠·시드·명령 순서로 재현하며 네이티브와 WASM의 비트 단위 일치를 자동 보장하지 않습니다.

## 채굴 보조와 카드 성장의 상태 경계

Q-09=A와 후속 답변으로 안전한 시작 구역·정비당 무료 스캔 1회·조기 정비 종료를 선택했습니다. 스캔은 광부가 접근 가능한 갱도 경계의 미굴착 1칸에서 광물·둥지 유무·숫자를 공개하며 굴착 횟수·자원을 바꾸지 않습니다. Q-03 후속으로 현재 이동·굴착 완료 뒤 사용자 준비 완료로 종료합니다. 숫자 0 정보 연쇄 공개와 실제 둥지의 다음 공세 예약도 확정했습니다. 안전 구역 크기·초기 공개·추가 적 수는 수치 초안으로 제안합니다. 아래는 이 규칙의 구현 제안입니다.

정비 상태에는 남은 굴착 수와 스캔 잔여 횟수를 별도로 둡니다. 스캔 1회는 정비 단계에 실제 진입할 때 한 번 초기화하고 메뉴 재진입·지상 재배치 뷰 전환·리사이즈에서는 초기화하지 않습니다. 접근 가능한 열린 작업 칸에 상하좌우로 접한 미굴착 목표인지와 잔여 횟수를 검사한 뒤 선택 1칸의 공개 정보와 스캔 차감을 함께 적용하는 안입니다. HUD에는 그 칸의 공개 결과만 전달합니다.

스캔으로 공개된 정보와 실제 굴착 상태는 구분합니다. 스캔은 미굴착 상태·광물 재고·금 잔액·남은 굴착을 유지하고 둥지 처리나 추가 공세 예약을 발생시키지 않습니다. 선택 1칸의 숫자가 0이어도 스캔이 주변 칸의 연쇄 공개로 바뀌지 않도록 하는 안입니다. 실제 굴착은 이후 도구 등급·작업 접근을 따로 검사하며 보상·작업 소모를 한 번 적용합니다. 중복 스캔·이미 아는 칸의 처리와 같은 세부 거절 정책은 첫 명령 규칙에서 명시합니다.

준비 완료 명령은 정비 단계와 광부의 유휴 상태를 검사하는 안입니다. 이동·굴착 중에는 거절하고 요청을 예약하지 않으며 현재 작업을 취소하지 않습니다. 작업 완료 뒤 사용자가 다시 눌러 성공한 단계 전환에서만 미사용 굴착 정리·손패 재구성·다음 웨이브 준비를 한 번 수행합니다. 작업 완료는 게임 시간이 결정하며 버튼 표시·Lottie 재생 완료를 기준으로 삼지 않습니다. 종료 실패나 중복 입력이 작업 보상·무료 스캔·손패를 다시 생성하지 않아야 합니다. 안전 시작 구역과 추측 없이 진행할 수 있는 범위는 실제 보드에서 검증합니다.

### 숫자 정보와 실제 지형·둥지 처리

숫자 공개 상태와 광물 정보·실제 굴착 상태를 구분하는 안입니다. 숫자만 알려진 미굴착 암반은 광부가 통과할 수 없고 광물을 주지 않습니다. 스캔은 해당 칸의 광물·둥지·숫자를 공개하지만 갱도를 열지 않으며, 0 연쇄 공개는 연결 영역과 경계의 숫자 정보만 추가합니다. 화면도 숫자 표시와 암반 제거를 구분합니다.

연쇄 공개의 이웃은 단서의 8방향을 사용하고 실제로 굴착한 둥지 없는 0칸에서 시작하는 세부안을 제안합니다. 0 이웃을 순회해 연결 영역과 경계 숫자를 모으되 같은 칸을 중복 처리하지 않습니다. 플레이어 표식은 추측이므로 최초 둥지 배치를 대신하지 않습니다. 둥지 칸은 주변 둥지 수가 0이어도 안전 칸의 연쇄 공개 시작점으로 삼지 않는 안입니다. 스캔으로 본 0은 선택 1칸 공개를 유지합니다.

실제 둥지 굴착 완료 결과는 원본 칸과 대상 다음 웨이브를 식별해 추가 공세에 한 번 반영합니다. 정보 공개·스캔·같은 칸 재처리로 예약하지 않습니다. 정비에는 다음 공세의 추가 적을 예고하고 예약된 웨이브에서 한 번 소비합니다. 즉시 광부 피해는 없으므로 첫 규칙에 광부 HP·채굴 전투를 추가할 필요가 없습니다. 추가 적 수는 콘텐츠 수치이며 새 판에서 처리 기록·예약을 함께 초기화합니다.

### 건물 카드 행동과 손패 교환

Q-06=A로 건물 카드는 빈 패드 설치·동종 강화·다른 종류 교체에 쓰고 전투 에너지로 손패를 교환합니다. 카드 사용 검사는 카드 행동 분류와 목표 상태로 설치·강화·교체 중 적용할 결과를 결정하는 안입니다. 동종 여부는 CardInstanceId가 아니라 건물 정의 ID로 비교합니다. 유닛 카드 사용은 새 UnitState 소환이며 기존 유닛의 강화로 해석하지 않습니다.

설치에서는 허용 패드·점유, 강화에서는 대상 종류·현재 레벨·상한, 교체에서는 기존 대상·후속 건물의 설치 조건을 검사합니다. 모두 카드·에너지·단계 조건을 먼저 확인한 뒤 결과를 적용합니다. 교체 대상부터 제거하고 새 건물 생성에 실패하는 부분 변경을 만들지 않습니다. 교체 레벨·환급·손실과 각 행동의 실제 비용은 미정이며 확정 전에는 고정된 규칙으로 만들지 않습니다.

손패 교환은 획득 카드 교체와 별도 명령으로 두는 안입니다. 전자는 활성 덱의 카드 인스턴스 수를 유지하는 순환, 후자는 기존 1장을 새 1장으로 바꾸는 구성 변경입니다. 교환의 선택 카드·순서·허용 조건은 아직 제안이며 확정 뒤 에너지 소비와 손패·대기열 변경을 함께 검증합니다. 같은 입력이 Pointer Events와 후속 클릭에서 중복 적용되지 않도록 웹 경계에서도 확인합니다.

### 개별 레벨과 공통 장비

Q-10=A로 에너지는 개별 타워 레벨, 광물은 도구·공통 장비, 룬은 후속 공격 방식 분기로 역할을 정했습니다. TowerState에는 해당 타워의 레벨을 두고 CardDefinition은 공유하는 읽기 전용 정의로 유지합니다. 타워 하나를 강화할 때 같은 종류의 다른 타워나 카드 정의의 레벨을 함께 변경하지 않습니다.

공통 장비는 RunState의 장비 상태로 관리하고 대상 종류의 기존·신규 개체에 같은 계산을 적용하는 안입니다. 실제 능력치는 정의·개별 레벨·공통 장비에서 구하며 계산된 능력치를 다시 원본처럼 누적해 장비가 중복 적용되지 않게 합니다. 경비병 장갑의 최대 HP·현재 HP 정책은 별도 선택이 남아 있고 무료 재배치·덱 교체·공통 장비 적용이 의도하지 않은 치료로 바뀌지 않아야 합니다.

룬은 이 계산에 실제 분기가 필요해지는 후속 단계에서 추가합니다. 역할을 선택한 것만으로 룬 비용·구매 횟수·중첩·전체 룬 시스템을 첫 연결판에 구현하지 않습니다.

## 표현과 ThorVG 렌더러

게임 표현 계층은 공개 정보·좌표·미리보기·에셋 키·연출 결과를 구성합니다. 엔진의 렌더러는 Shape·Picture·Animation과 캔버스 수명을 소유합니다. 게임 표현이 적·카드별 외형을 선택하고 엔진은 일반 그리기와 자원 수명을 제공합니다. 실제 둥지 전체 배열을 HUD에 전달하지 않고 공개 보드만 사용합니다. 전체 RunState를 매 프레임 JS로 복사하지 않습니다.

에셋 원본과 애니메이션 인스턴스의 수명을 구분하고 선택한 ThorVG 버전의 소유권 규칙을 확인합니다. 같은 Lottie 파일을 쓴다고 모든 재생 상태가 자동 공유된다고 가정하지 않습니다.

Rubiks의 FrameInputs·surface frame 변경 감지는 정지 화면·HUD에 참고할 수 있습니다. 전투는 계속 바뀌므로 적·탄환·Lottie가 그리는 비용 자체를 측정해야 합니다. 장면 재사용·정적 지형 유지·개체 회수 정책을 장면 규모에 맞춰 비교합니다.

첫 렌더러와 표시 경로를 측정한 뒤 CPU·WebGL의 차이가 드러나는 경계를 구체화합니다. CPU 픽셀 버퍼와 putImageData는 CPU 표시 어댑터의 책임이고 모든 backend에 필요한 계약으로 강제하지 않습니다. 미래 backend만을 위한 범용 renderer hierarchy는 우선 만들지 않습니다.

## 콘텐츠·WASM·웹 경계

카드·적·공세·재료·레시피·능력·외형 정의는 검증한 카탈로그로 읽습니다. JSON은 후보이며 파서·스키마·버전은 첫 구현에서 선정합니다. 파일 I/O·파서는 규칙 밖에서 값을 변환하고 비용·참조·진행 조건을 검사합니다.

제작 광물 재고와 금 재화 잔액은 RunState에서 구분하는 안입니다. 금 광맥을 캐면 잔액에 바로 더하고 광석 재고와 중복 지급하지 않는 방식을 추천합니다. 전투 에너지는 별개입니다. 금 모집은 Q-23=A로 유닛 카드 3택1이며 획득 카드는 기존 1장과 교체해 활성 8장을 유지합니다. Q-20 후속으로 후보 확인 무료·교체 확정 시 결제·취소 무소모·동일 후보 유지를 정했습니다. 보유 종류 포함·후보 3종 서로 다름도 확정했습니다. 종류별 콘텐츠·성공 뒤 재모집·모집 기회 만료는 미정이고 모집 자체는 전장 슬롯 포화 때문에 거절하지 않습니다. 상세 역할은 [경제안](economy-plan.md)을 따릅니다.

모집 후보는 OfferId와 서로 다른 유닛 카드 정의 ID 3개를 가진 판의 상태로 보존하는 안입니다. 활성 덱에 있다는 이유로 해당 종류를 제외하지 않으며 같은 종류의 카드 인스턴스 여러 장을 서로 다른 후보로 세지 않습니다. 첫 풀이 경비병·사수·폭파병 3종이면 항상 세 종류 전부를 제시하고, 더 큰 풀의 추첨 정책은 확장 때 정합니다. 금이 부족해도 후보 확인 자체는 무료이며 UI 재진입은 같은 후보를 읽습니다. 취소는 금·활성 덱·최근 획득 기록을 바꾸지 않고 후보 상태도 유지합니다. 미확정 카드·교체 대상 선택은 UI 상태로 둘 수 있지만 실제 카드는 교체 확정에서만 지급합니다. 유효 후보 3개를 만들 수 없으면 금 소모 없이 이유를 표시하는 안입니다.

교체 확정은 RunId·OfferId·선택한 후보 정의 ID·제거할 CardInstanceId를 받아 현재 단계·유효 후보·활성 덱 소속·표시 가격 조건과 현재 금 잔액을 다시 검사하는 안입니다. 새 카드 선택 후 다른 정비에 금을 써 잔액이 줄어도 부분 교체가 일어나지 않아야 합니다. 성공 시 금 차감·기존 1장 제거·새 인스턴스 1장 생성·최근 획득 기록·해당 모집 기회 소비를 함께 확정합니다. 실패 시 금·덱·후보를 보존하고 이미 소비한 OfferId의 재처리는 거절합니다. 실제 소환 에너지·전장 유닛·사용 슬롯은 이 명령으로 바꾸지 않습니다. 성공 뒤 새 모집 후보를 언제 만드는지와 모집 기회의 유효 범위는 후속 정책으로 정합니다.

기본 몬스터와 후속 유저 데이터는 같은 검증·규칙 경로를 쓰는 방향입니다. 네임스페이스·버전·외형 참조·생성 예산은 실제 팩 도입 시 계약을 구체화합니다. 첫 연결판에 제작실·동적 팩·스크립트 런타임을 포함하지 않습니다.

web/wasm 어댑터만 C ABI와 heap에 접근합니다. 생성·명령·프레임 갱신·필요 HUD·리사이즈·해제의 좁은 경계로 시작합니다. 개체마다 JS에서 위치·Lottie 프레임을 호출하지 않습니다. export 이름뿐 아니라 필드 타입·단위·메모리 성장·재시작 뒤 view 갱신을 검증합니다.

웹은 입력·HUD·로딩·오류·페이지 수명과 저장 어댑터를 맡습니다. 게임 규칙의 권위 상태를 웹에 중복 소유하지 않습니다. 입력 취소와 listener·루프 해제를 WASM 해제보다 먼저 처리합니다.

| thorium_client 및 WASM 실행 | 앱·게임 표현·로딩·엔진·바인딩 수명 조합 |
| 필요한 네이티브·웹 테스트 | 규칙·좌표·엔진 자원·콘텐츠 로딩·실제 ABI 검증 |

게임 표현의 순수 좌표·표시 모델은 ThorVG 없이 필요한 소스만 연결해 테스트할 수 있습니다. 별도 presentation 라이브러리나 폴더마다 독립 타깃을 요구하지 않습니다. 엔진 모듈을 두는 것과 범용 ECS·플러그인·외부 배포 패키지를 만드는 것은 별도 선택입니다.

Catch2·Vitest·Playwright는 Rubiks의 검증 구성을 참고하는 후보입니다. 선정 버전과 도입 범위는 첫 구현 계획에 명시합니다. 타입·언어에 맞는 문서 주석을 작성하고 실제 버그를 막는 테스트를 둡니다.

## 플레이 사양과 첫 구현의 경계

[첫 3웨이브 플레이 사양](first-playable-spec.md)의 P-01~P-10은 이번 검토용 기본값 묶음입니다. 전투마다 에너지 초기화·수동 시작, 건물 3레벨, 무료 정비 위치 교환·무환급 해산, 명령 단계 뒤 일반 공격의 피해 일괄 반영, 재시작·저장 범위를 제안합니다. 이 세부안을 사용자 확정값으로 자동 승격하지 않습니다.

첫 공격 표현은 즉시 피해 판정과 별도 탄환 연출을 추천하므로 이를 위해 비행 탄환의 충돌·유도 규칙을 먼저 만들지 않습니다. 공격 단계 시작 시 유효한 일반 공격 결과를 모아 피해를 함께 적용하고 사망 정리 뒤 거점 도달을 처리하는 안입니다. 명령 단계의 마법 사망은 일반 공격 대상을 고를 때 이미 제외합니다.

정비 유닛 위치 교환·해산·치료는 서로 다른 검증과 명령으로 둡니다. 위치 교환은 양쪽 위치를 함께 검사하고 ID·HP·슬롯을 유지하며, 해산은 실제 제거와 슬롯 반환을 처리하고, 치료는 자원과 HP를 바꿉니다. 게임 코드로 옮기기 전에 채택할 추천값·파일·의존성·회귀 사례를 명시합니다.

## 검증과 다음 단계

구현 시 다음을 확인합니다.

- 규칙·좌표 테스트를 브라우저와 GPU 없이 실행.
- 뷰 전환 시 지상·지하·재료 유지, 새 판에서 모두 초기화.
- 같은 tick의 사망·도달·종료 우선순위, 저지·표적 참조 정리.
- DPR·resize·카메라 변환과 역변환, 드래그 취소.

- 실패한 명령·제작·로딩이 상태를 부분 변경하지 않음.

- 정비 중 지상 재배치·모집 UI를 열어도 전투가 시작되지 않으며 선택할 취소·교체 정책을 지킴.
