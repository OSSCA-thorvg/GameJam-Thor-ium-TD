# SDL 기반 데스크톱·웹·공통 UI 제안

작성일: 2026-11-03, 갱신일: 2026-11-04. 사용자의 Windows·macOS 실행과 공통 터치·UI 구현 아이디어를 검토한 **미확정 제안**입니다. 2026-11-04 SDL을 포함한 구조도 요청에 따라 아래 큰 구조와 정보 흐름을 구체화했습니다. SDL3 버전·빌드 방식·UI 구현 범위와 새 실행 환경의 완료 기준은 아직 확정하지 않았습니다. [엔진 경계 수정안](architecture-overview.md)과 함께 검토합니다.

## 제안의 핵심

2026-11-04 첫 시연판은 A의 공통 C++ UI 방향으로 구현했고, SDL 3.4.18·ThorVG의 고정 커밋을 사용했습니다. 아래 제안은 전체 UI·출시 플랫폼의 검토 범위를 보존한 것으로, 실제 구현·테스트와 선택한 개발 의존성은 [첫 구현 기록](implementation-v0.1.md)과 [의존성 잠금](../dependencies.lock.json)을 따릅니다.

**SDL3로 플랫폼을 연결하고, ThorVG로 게임과 UI를 그리며, C++의 작은 UI 계층을 웹과 데스크톱에서 공유하는 안을 추천합니다.** 기존 웹 중심 구조에서 HTML HUD가 맡던 손패·정비·팝업을 공통 게임 UI로 옮기는 선택입니다. 웹 배포는 유지하고 Windows·macOS에서는 같은 C++ 소스를 네이티브 실행 파일로 빌드합니다. 동일 실행 파일을 모든 플랫폼에 배포한다는 뜻은 아닙니다.

SDL3 공식 플랫폼 목록에는 Windows·macOS·Emscripten이 있고, 터치 API는 지원 기기에서 여러 손가락을 추적합니다. 이는 프로젝트의 각 플랫폼 빌드·터치 동작을 검증했다는 의미가 아닙니다. [SDL 플랫폼](https://wiki.libsdl.org/SDL3/README-platforms), [터치 입력](https://wiki.libsdl.org/SDL3/CategoryTouch)

## SDL 반영 구조도 — 2026-11-04

큰 구조는 **App / Game rules / Game presentation / Engine / SDL platform adapter**로 구분합니다. 엔진 내부에서는 UI·입력과 ThorVG 그래픽을 따로 보여줍니다. 에셋·시간 도구는 엔진에 포함하고 상세 노드는 생략합니다.

~~~mermaid
flowchart TB
    app[App: 실행·수명·호출 순서] --> rules[Game rules: 판 상태·전투·카드·채굴]
    app --> view[Game presentation: 지상·지하·손패·정비창]
    app --> sdl[SDL 플랫폼 어댑터: 창·이벤트·출력]
    view -->|공개 정보 계약| rules
    subgraph engine[Engine: 에셋·시간 도구 포함]
        ui[UI / Input: 배치·버튼·포커스·입력 소유]
        render[Graphics: ThorVG·Lottie·텍스트]
        ui --> render
    end
    view --> ui
    view --> render
~~~

화살표는 **주요 코드 의존 방향**입니다. 실제 앱은 엔진 초기화·일반 입력·시간 도구도 조합합니다. 그림은 모든 함수 호출이나 include를 나열하지 않습니다. SDL 어댑터가 이벤트를 공통 입력 값으로 바꾸고 앱이 이를 엔진 입력·UI에 전달합니다. 엔진 UI·그래픽에서 게임 코드나 SDL 이벤트 타입을 참조하지 않으며 게임 규칙은 SDL·ThorVG 없이 검증합니다. SDL의 사용 위치는 플랫폼 어댑터와 이를 조합하는 앱 경계입니다.

### 재생하는 입력 → 화면 흐름

1. **입력:** SDL 어댑터가 창·마우스·터치 이벤트를 공통 값으로 변환하고, 앱이 엔진 UI에 전달해 포인터 소유·포커스 등을 처리합니다.
2. **명령:** 일반 UI 동작을 게임 화면이 카드 사용 같은 의도로 해석하고 앱이 게임 명령을 전달합니다. UI가 잡은 입력이 월드 선택으로 중복 전달되지 않게 합니다.
3. **규칙:** 판의 단계·대상·에너지·슬롯 등을 검사해 성공한 상태 변경만 반영합니다. 실패하면 비용·판 상태를 보존합니다.
4. **그리기:** 앱이 공개 결과를 읽어 게임 화면·공통 UI를 구성하고, ThorVG로 월드와 UI를 그린 뒤 SDL 어댑터가 출력에 연결합니다.

실행 그림의 UI → 게임 화면 화살표는 앱이 전달하는 UI 동작 값의 흐름입니다. 엔진 UI에서 게임 화면을 include하거나 카드 규칙을 직접 호출하는 의미는 아닙니다. 게임 규칙이 공개 결과를 내보내도 코어의 소스 의존은 표현으로 향하지 않습니다. 입력이 없는 게임 tick·정비 작업은 별도 시간 정책을 유지합니다.

Windows·macOS에서는 네이티브 실행 파일, 웹에서는 Emscripten/WASM으로 빌드하는 목표입니다. 게임·UI C++ 코드를 공유하고 필요한 브라우저 연결만 남기는 안이며, 각 환경의 빌드·실행·성능을 확인한 상태는 아닙니다.

## 라이브러리와 우리 코드의 역할

| 영역 | 역할 | 경계 |
| --- | --- | --- |
| SDL 플랫폼 어댑터 | 창·시스템 이벤트·마우스·키보드·지원 기기의 터치, 실행과 출력 연결 | SDL 이벤트를 게임 규칙으로 직접 전달하지 않음 |
| Engine input / UI | 공통 포인터 의도, UI 배치·히트 테스트·포커스·입력 소유·기본 컨트롤 | 카드 비용·굴착 횟수·모집 결제를 결정하지 않음 |
| Engine render | ThorVG 도형·텍스트·Lottie와 렌더 자원 수명 | 카드·적 종류의 의미를 모름 |
| Game presentation | 손패·광물 HUD·제작·정비·모집창과 지상·지하 화면 구성 | 표시 상태와 사용자 선택을 명령에 연결 |
| Game rules | 명령 검증·판 상태·전투·채굴·비용·보상 | SDL·ThorVG·UI 위젯 없이 테스트 |
| App | 입력 전달·게임 갱신·화면 구성·그리기의 순서와 수명 조합 | 세부 게임 규칙을 UI에 복제하지 않음 |

SDL을 도입해도 이 게임의 버튼·손패·팝업 동작이 자동으로 만들어지지는 않습니다. SDL의 창·입력 기반 위에 필요한 UI 기능을 제공하는 구상입니다. SDL의 역할은 [공식 저장소](https://github.com/libsdl-org/SDL), 일반 입력·텍스트 입력은 [SDL_Event](https://wiki.libsdl.org/SDL3/SDL_Event)와 [SDL_StartTextInput](https://wiki.libsdl.org/SDL3/SDL_StartTextInput)에서 확인했습니다.

## 공유할 UI의 범위 세 안

| 안 | 구성 | 이점 | 비용 |
| --- | --- | --- | --- |
| A · 작은 C++ 공통 UI · 추천 | SDL 입력 + 자체 UI 동작 + ThorVG 표시를 전 플랫폼에서 사용 | 화면·입력 코드를 공유하고 ThorVG 중심의 외형을 유지 | 배치·포커스·스크롤·클리핑 등 필요한 UI 기반 제작 |
| B · 웹 HTML / 네이티브 C++ UI | 규칙·표현 모델은 공유, 화면 위젯은 플랫폼별 구현 | 웹에서 기존 DOM 기능을 활용 | 손패·정비 등의 두 UI 구현을 유지해야 함 |
| C · 외부 C++ UI 라이브러리 | SDL에 RmlUi 같은 UI 라이브러리를 조합 | 기존 레이아웃·컨트롤 기능 활용 | 추가 의존성과 렌더링 통합 검증 |

RmlUi는 HTML/CSS 계열 C++ UI 라이브러리이며 SDL 플랫폼과 여러 렌더러를 제공합니다. 확인한 제공 렌더러 목록에는 ThorVG가 없고, 자체 렌더 인터페이스는 인덱스 삼각형 등을 처리합니다. 따라서 ThorVG로 모든 UI를 그리는 A와 같은 비용으로 통합된다고 가정하지 않습니다. [공식 RmlUi 저장소](https://github.com/mikke89/RmlUi), [렌더 인터페이스](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/interfaces/render.html)

## A를 선택했을 때의 작은 UI 기반

첫 UI 후보는 패널·텍스트·버튼·게이지·손패 카드·모달입니다. 이 화면들에 필요한 가로/세로 배치·여백·정렬·클리핑·포커스·입력 소유를 먼저 설계합니다. 스크롤 목록은 모집·정비 화면에 실제로 필요할 때 추가합니다. 모든 HTML/CSS 기능·테마 편집기·범용 UI 디자이너를 구현하는 범위는 아닙니다.

- 공통 UI는 눌림·포인터 소유·포커스를 유지하고, 게임 화면이 위젯을 구성합니다. 게임 개체에 동일 UI 베이스 클래스를 강제하지 않습니다.
- 마우스·터치를 포인터 ID가 있는 공통 입력으로 정규화합니다. 손패 드래그나 탭→대상 선택은 최종적으로 같은 게임 명령을 만듭니다.
- UI가 소유한 입력은 월드 선택으로 중복 전달하지 않습니다. 카드 드래그의 월드 대상 선택은 명시적 카드 사용 흐름으로 연결합니다.
- 입력 취소·포커스 상실·리사이즈에서 미확정 조작을 정리합니다. 모달을 누르거나 카드 드래그를 취소해도 카드·에너지·광물은 바뀌지 않습니다.
- 화면 폭에 따라 동일 UI의 배치를 바꾸고, 터치 영역·키보드 포커스 이동·확인/취소를 함께 설계합니다. 자체 UI의 접근성 의미 제공도 별도 설계 항목으로 둡니다.
- 한글 표시와 한글 입력은 구분합니다. 사용자 몬스터 이름 같은 텍스트 편집이 필요해질 때 조합 입력·캐럿·선택·화면 키보드를 검증하며, 초기 UI에 텍스트 편집기가 자동 포함되지는 않습니다.

SDL은 터치에서 마우스 이벤트를 합성할 수 있으므로 두 경로를 동시에 처리해 카드가 두 번 사용되지 않게 정책을 정합니다. [터치→마우스 합성 설정](https://wiki.libsdl.org/SDL3/SDL_HINT_TOUCH_MOUSE_EVENTS)

창의 논리 크기·출력 픽셀 크기·UI 배율을 구분하고 입력·그리기에 같은 변환을 적용합니다. SDL 렌더러 전용 변환 함수를 ThorVG 경로에도 무조건 적용하지 않습니다. [SDL High DPI](https://wiki.libsdl.org/SDL3/README-highdpi)

## 폴더 B 안의 위치 후보

~~~text
src/
  engine/
    input/          # 공통 입력 값·조작 상태
    ui/             # 배치·포커스·기본 컨트롤
    render/         # ThorVG·Lottie·그리기
    assets/
    time/
  game/
    rules/          # 세션·전투·카드·채굴·제작
    presentation/   # 게임 화면·손패·정비 UI 구성
  app/              # 실행·수명 조합
  platform/
    sdl/            # SDL 이벤트·창·표시 연결
    web/            # 필요한 Emscripten·브라우저 연결만
web/                # HTML 로딩·캔버스 호스트 후보
content/
tests/
docs/
~~~

`platform/sdl/`은 Windows 전용이 아닙니다. SDL을 Emscripten으로 빌드한 웹에서도 같은 플랫폼 계층을 쓰는 안입니다. 웹 쪽 DOM 입력 리스너를 중복 설치해 동일 조작을 두 번 전달하지 않습니다. 파일·저장·브라우저 수명처럼 실제 차이가 남는 부분만 추가 어댑터를 둡니다. 경로와 파일은 후보이며 미리 빈 폴더를 생성하지 않습니다.

## ThorVG와 SDL의 표시 경로

ThorVG 공식 예제의 `Example.h`는 SDL2 기반 창·이벤트 및 ThorVG 캔버스 조합을 보여줍니다. SDL3로 그대로 복사 가능한 코드는 아니므로 버전·초기화·메모리·출력 계약을 따로 검증합니다. [공식 예제 코드](https://github.com/thorvg/thorvg.example/blob/main/src/Example.h)

첫 기능 연결 후보는 ThorVG 소프트웨어 출력 버퍼를 SDL 텍스처에 올려 표시하는 경로입니다. 이는 버퍼·stride·픽셀 형식·알파·리사이즈를 눈으로 검증하기 쉬운 실험안입니다. 물량 전투의 최종 성능 기준을 만족한다는 의미는 아닙니다. 전체 화면 전송 비용을 측정하고 GPU 경로와 비교할 수 있게 표시 어댑터를 구분합니다. 모든 백엔드를 CPU 픽셀 버퍼 계약으로 고정하지 않습니다.

SDL3 자체가 기존 WASM 경로보다 더 빠르다는 결론은 내리지 않습니다. 이번 선택의 주된 목적은 네이티브 실행과 공통 입력·UI입니다.

## 실행과 검증 순서 제안

1. macOS 네이티브와 웹에서 같은 버튼·카드·한글 텍스트·Lottie 하나를 표시하는 작은 실행 검증부터 합니다. Windows는 별도 빌드·실행 환경을 확보해 같은 시나리오로 확인합니다.
2. SDL 이벤트를 공통 입력으로 바꾸고 클릭/탭·카드 드래그·취소·포커스 이동을 검증합니다. 터치는 실제 지원 기기·브라우저 결과를 따로 기록합니다.
3. 1·2가 연결되면 이미 제안한 첫 3웨이브 게임을 붙입니다. 네이티브·웹에서도 동일 명령열의 규칙 결과를 비교합니다.

웹은 브라우저에 제어를 돌려주는 실행 방식이 필요합니다. SDL3의 main callback 구성을 후보로 두고 앱 수명과 결합합니다. 자산 로딩·저장·탭 복귀도 검증하며 기존 Pages 하위 경로 요구를 유지합니다. [SDL 실행 콜백](https://wiki.libsdl.org/SDL3/README-main-functions), [Emscripten 안내](https://wiki.libsdl.org/SDL3/README-emscripten)

위 항목은 **앞으로 수행할 게임·플랫폼 테스트**입니다. 이 문서 작성이나 문서 테스트 통과가 SDL 통합·Windows/macOS 실행·터치·성능 검증을 대신하지 않습니다. 실제 구현 전 SDL/ThorVG 버전, 빌드 도구 조합, 첫 파일과 테스트 범위를 검토합니다.
