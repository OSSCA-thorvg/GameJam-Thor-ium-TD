# 큰 구조와 폴더 배치 비교

갱신일: 2026-11-03. 사용자는 **폴더 B: 실행 경계 + 기능별**을 선택했고, 아키텍처 B에서도 엔진 경계를 별도로 드러내야 한다고 지적했습니다. 아래는 그 피드백을 반영한 수정안입니다. 엔진 세부 범위·정확한 폴더 이름·빌드 타깃·게임 구현은 아직 검토 대상입니다. [결정 기록](decisions.md)의 D-60·D-61과 [상세 아키텍처](architecture.md)를 함께 확인합니다.

## 모든 후보에서 지킬 기준

- 한 판의 권위 상태는 한 곳에서 소유합니다. 웹 HUD나 Lottie가 체력·보상·굴착 결과를 따로 결정하지 않습니다.
- 지상과 지하는 같은 판의 상태를 보여주는 두 뷰입니다. 뷰를 전환해도 유닛·광물·덱이 유지됩니다.
- 게임 시간과 화면 애니메이션 시간을 구분합니다. 렌더링 빈도가 피해·채굴 결과를 결정하지 않습니다.
- 수치·맵·카드 정의와 플레이 중 바뀌는 인스턴스를 구분합니다. 외부 파일은 검증 뒤 규칙에 전달합니다.
- 규칙을 브라우저·ThorVG 없이 검증할 수 있게 합니다. 이 경계를 함수·모듈·빌드 타깃 중 어디까지 강제할지는 후보별로 다릅니다.

여기서 ‘엔진 아키텍처’는 이 게임을 실행하는 구조를 뜻합니다. 범용 엔진의 ECS·SceneTree·플러그인 체계는 필요성이 확인될 때 검토합니다. C++/WASM·얇은 웹 셸·ThorVG는 기존 실행 구성의 후보를 유지하며, 아래 세 안은 그 안의 책임 배치를 비교합니다.

## B 수정안: 게임 규칙·게임 표현·엔진을 구분

초기 비교는 엔진 분리와 범용 엔진 제작을 같은 선택지처럼 설명했습니다. **규칙과 표현을 분리하는 B에서도 엔진 기반은 별도 모듈로 둘 수 있습니다.** 게임을 위한 명확한 엔진 경계를 두는 것과 여러 게임을 지원하는 편집기·ECS·플러그인 API를 설계하는 것은 서로 다른 결정입니다. 이전 C의 재사용·범용성 수준을 채택해야만 엔진을 분리할 수 있는 것은 아닙니다.

| 책임 | 소유하는 것 | 게임에 남기는 것 |
| --- | --- | --- |
| Engine | ThorVG·Lottie 자원, 그리기, 에셋 수명, 일반 좌표 변환, 고정 tick 누산 등 실행 도구 | 피해·저지·카드·굴착·보상·전투/정비 정책 |
| Game rules | 판 상태, 전투·카드·채굴·제작, 명령 검증과 상태 변경 | ThorVG·브라우저 호출 |
| Game presentation | 지상·지하 화면 구성, 공개 정보, 외형·연출 선택, 논리 대상 해석 | 실제 렌더 자원의 세부 수명 관리 |
| App | 엔진·판·표현의 생성과 해제, 로딩 조합, 갱신·그리기 호출 순서 | 개별 카드·적·광물의 규칙 분기 |
| Platform / Web | WASM 연결, 브라우저 입력·HUD·페이지 수명 | 게임의 권위 상태 |

예를 들어 게임 규칙이 적의 피해와 사망을 결정하고, 게임 표현이 그 결과에 맞는 위치·외형·피격 연출을 선택하며, 엔진이 도형·Lottie를 갱신하고 그립니다. 엔진은 경비병·채굴 광물·카드 비용을 알 필요가 없습니다.

### 코드 의존 방향

~~~mermaid
flowchart TB
    platform[Platform / Web: 웹·WASM 연결] --> app[App: 실행·수명 조합]
    app --> rules[Game rules: 판 상태·규칙]
    app --> view[Game presentation: 지상·지하 화면 구성]
    app --> engine[Engine: 그리기·에셋·변환·시간 도구]
    view -->|공개 정보 계약| rules
    view --> engine
~~~

이 그림의 화살표는 **소스 코드가 사용하는 방향**입니다. 엔진에서 게임으로 향하는 의존은 두지 않습니다. 첫 규칙 코어는 ThorVG와 엔진 렌더 모듈 없이 빌드·검증하는 안입니다. 게임 전용 SurfacePoint·MineCell과 일반 화면 변환 도구의 경계는 유지합니다.

### 실행·정보 흐름

~~~mermaid
flowchart LR
    input[입력] --> app[App]
    app --> rules[명령 검사·게임 갱신]
    rules -->|공개 상태·확정 결과| view[Game presentation]
    app -->|그리기 요청| view
    view --> engine[Engine: 그리기]
    engine --> output[화면 출력]
~~~

실행 중 코어의 결과를 표현이 읽는 것과, 소스 코드에서 코어가 표현을 참조하는 것은 다릅니다. 전체 판 상태를 매 프레임 JS에 복사하지 않고 필요한 공개 정보와 HUD 계약을 사용합니다. 미공개 둥지 정보는 표시 경계에서 제외합니다.

엔진의 고정 tick 도구는 주어진 경과 시간으로 갱신 횟수를 계산합니다. 전투가 언제 흐르고 정비 중 어떤 작업만 진행되는지는 게임·앱 정책입니다. 브라우저의 탭 숨김·시간 입력은 웹 어댑터와 앱이 연결하고, 엔진 안에 전투 단계 분기를 넣지 않습니다.

### 모듈과 빌드 타깃

별도 `engine/` 책임 경계는 수정안에 명시합니다. `thorium_engine`·`thorium_rules`·최종 클라이언트 타깃으로 검증하는 구성을 추천하며 정확한 타깃은 첫 구현 계획에서 결정합니다. 엔진에는 게임 의존을 허용하지 않고, 규칙 테스트에는 렌더러를 연결하지 않는 방식으로 경계를 검사할 수 있습니다. 폴더마다 라이브러리를 추가하거나 엔진을 외부 패키지로 배포할 필요는 없습니다.

## 폴더 배치 후보

| 안 | 묶는 기준 | 장점 | 비용·주의점 |
| --- | --- | --- | --- |
| A · 기술 계층별 | 상태·규칙·표현·렌더링을 각각 모음 | 의존 방향과 기술 역할을 찾기 쉬움 | 전투 기능 하나의 수정이 여러 폴더로 흩어짐 |
| B · 실행 경계 + 기능별 · 사용자 선택 | 엔진·게임·앱·플랫폼을 구분하고 게임 규칙 안은 전투·카드·채굴로 나눔 | 테스트 경계와 기능 탐색을 함께 드러냄 | 여러 기능을 함께 바꾸는 처리는 세션이 조정해야 함 |
| C · 기능 안에 규칙·표현 | 전투·채굴 같은 기능 아래 관련 규칙과 화면 코드를 모음 | 한 기능의 작업을 가까이 모을 수 있음 | 기능 간 계약과 규칙의 렌더러 미의존을 파일·빌드 규칙으로 지켜야 함 |

폴더 B의 묶는 기준은 사용자 선택으로 기록했습니다. A·C는 비교 자료로 남깁니다. 아래 B의 구체 경로는 엔진 경계를 반영한 수정 제안이며 빈 폴더를 미리 생성하는 목록이 아닙니다. 폴더 수와 빌드 타깃 수를 일치시키지 않습니다.

### 폴더 A · 기술 계층별

~~~text
src/
  app/
  domain/          # 판·개체 상태와 타입
  systems/         # 전투·채굴 등의 규칙
  presentation/    # 뷰·좌표·표시 정보
  render/          # ThorVG·Lottie
  bindings/        # WASM 경계
web/               # 웹 셸
content/           # 수치·맵 정의와 외형 파일
tests/
docs/
~~~

### 폴더 B · 실행 경계 + 기능별

~~~text
src/
  engine/          # 그리기·에셋·일반 변환·시간 도구
  game/
    rules/         # 브라우저·ThorVG 미의존
      session/     # 판 상태·단계·기능 조정
      combat/
      cards/
      mining/
      crafting/
    presentation/  # 이 게임의 지상·지하 화면 구성
  app/             # 엔진·게임·표현의 수명과 실행 조합
  platform/        # C++ 쪽 WASM 어댑터
web/               # TypeScript 입력·HUD·페이지 수명
content/           # 수치·맵 정의와 외형 파일
tests/
docs/
~~~

이 구조에서 `game/presentation/`은 게임을 압니다. 일반 그리기·변환 도구는 `engine/`에 두고, 적·카드 외형 선택과 지상·지하 뷰 선택은 게임 표현에 둡니다. 카드·레시피 파일을 규칙 정의로 바꾸는 로딩 처리는 게임/앱 경계에서 검증하고 엔진의 범용 에셋 관리와 구분합니다.

### 폴더 C · 기능 안에 규칙·표현

~~~text
src/
  app/             # 판·기능 조정
  features/
    combat/        # 관련 규칙과 표현, 의존은 구분
    cards/
    mining/
    crafting/
  shared/          # 실제로 공유하는 타입·처리만
  platform/        # ThorVG·WASM·로딩
web/
content/
tests/
docs/
~~~

## 현재 선택과 다음 검토

Windows·macOS 네이티브 실행과 터치·UI 공유 아이디어에 따라 [SDL 기반 공통 UI 제안](cross-platform-ui-proposal.md)을 추가했습니다. 2026-11-04 요청으로 해당 문서에 App·게임 규칙·게임 화면·엔진 UI/그래픽·SDL 플랫폼 어댑터 구조도를 반영했습니다. 위의 초기 Platform / Web 노드보다 구체적인 현재 검토안입니다. 기존 웹 HUD 역할은 공통 C++ UI와 얇은 웹 호스트로 나누는 방향으로 그렸고, 구현·버전·배포 검증 범위는 별도로 결정합니다.

- 폴더의 큰 묶음은 B를 선택했습니다. 세부 경로는 위 수정안으로 제안합니다.
- B에서도 엔진 기반을 따로 드러낸다는 요구를 반영했습니다. 전체 상세 아키텍처를 승인한 것으로 확대하지 않습니다.
- 다음 확대 대상은 엔진 API와 게임 표현의 접점, 앱·판·렌더 자원의 소유권입니다. 클래스·ABI·세부 파일은 그 이후 구체화합니다.
