# 본격적인 개발 전 시작 계획

기준일: 2026-11-03. 사용자가 승인한 범위는 서브에이전트 조사와 규칙 선택지·아키텍처 문서 정리입니다. 개별 규칙 선택과 게임 코드·빌드 골격의 구현 승인은 구분합니다. 현재 게임 소스·새 의존성·배포 산출물은 생성하지 않았습니다.

## 먼저 읽을 순서

1. 이 문서에서 목표와 남은 결정을 확인합니다.
2. [첫 3웨이브 플레이 사양](first-playable-spec.md)의 남은 규칙·초깃값 추천 묶음을 검토합니다. 다른 안은 [규칙 선택지](rule-options.md)에서 비교합니다.
3. [아키텍처](architecture.md)의 책임·수명·좌표·시간 경계를 검토합니다.
4. 선택 결과를 [결정 기록](decisions.md)과 [프로토타입](prototype-plan.md)에 반영합니다.
5. 첫 실제 변경의 파일·의존성·테스트 범위를 확인하고 구현을 승인합니다.

조사의 근거는 [Rubiks·엔진 비교](architecture-research.md), 전체 게임 아이디어는 [통합 기획](game-design.md), 후속 사용자 제작은 [유저 콘텐츠 계획](../user-content-plan.md)에 있습니다.

## 게임의 중심과 지켜야 할 방향

Thor-ium TD의 중심은 **다수의 적에게서 거점을 지키는 카드 기반 타워 디펜스**입니다. 지하 채굴·제작·발견은 다음 방어의 선택을 바꿔야 합니다.

이미 선택한 방향은 지상 방어와 지하 채굴 연결, 타일 지정 후 광부 자동 이동·굴착, 최종 웨이브 생존 승리와 선택 심층 코어, 카드 행동 3분류, 플레이 중 카드 획득, 캐주얼 2D와 ThorVG·Lottie 활용입니다. 발견 도감의 부분 계승은 검토 방향이며 이번 판 전체 상태를 그대로 계승하는 것과 구분합니다.

2026-11-03까지 선택한 첫 검증 규칙은 다음과 같습니다.

- 화면·흐름: 지상 탑다운·지하 단면을 단계별 전환하고 전투·정비를 분리합니다. 정비당 5굴착, 추리 시간 제한은 없습니다.
- 카드: 기본 덱 8장·손패 4장, 획득 시 기존 1장 교체, 정비 후 최근 획득 우선 재구성입니다. 건물 카드는 설치·동종 강화·타종 교체, 손패 교환은 에너지를 사용합니다. 도감 선택 UI는 후속입니다.
- 유닛: 같은 카드로 반복 소환하며 기본 6슬롯·첫 유닛당 1슬롯입니다. 지정 위치 자동 교전·저지, 생존 유닛과 남은 HP 유지, 정비 재료 치료·무료 재배치를 지원합니다.
- 경제: 철·구리·수정은 도구·공통 장비 제작 광물, 에너지는 개별 타워 레벨과 카드 사용·교환 비용입니다. 금은 슬롯 상한 강화·유닛 카드 모집 재화입니다. 모집은 후보 3개 중 1개 획득·교체 확정 결제·취소 무소모·동일 후보 유지이며 실제 소환은 전투 에너지를 사용합니다.
- 전장: 정해진 웨이브 뒤 지상 확장을 선택하며 첫 검증은 2웨이브 뒤 1회입니다. 고정 적 경로·건물 패드·유닛 배치 칸부터 시작하고 자유 배치·경로 재계산은 후속 전환 방향입니다.
- 채굴 검증: 수작업 보드 1개, 열린 갱도 4방향 이동, 최초 둥지 8이웃 숫자, 안전 시작·무료 스캔 1회입니다. 스캔은 경계 1칸의 광물·둥지·숫자를 공개하고 굴착·자원을 바꾸지 않습니다. 현재 작업 완료 뒤 남은 굴착을 포기하고 조기 종료할 수 있습니다. 경로·수량·가격을 검증하고 자동 생성과 중력·사다리는 후속으로 둡니다.
- 환경: 데스크톱 60 FPS를 우선 검증하면서 모바일 UI·UX도 준비합니다. 구체 화면·입력 제안은 [UI·UX 계획](interface-plan.md)에 있습니다.

가격·후보 종류별 콘텐츠·재모집·회복량·유효 배치 칸·안전 구역 크기는 [플레이 사양](first-playable-spec.md)에 추천값을 준비했으며 아직 채택 전입니다. 실제 기준 환경도 남았습니다. 선택된 방식과 실제 보드·성능 검증 완료를 구분합니다.

## 추천 아키텍처의 요점

- 앱은 콘텐츠·렌더러·웹 수명을 소유하고 한 판은 GameSession이 소유합니다.
- 지상과 지하는 별도 상태·좌표·표현을 사용하고 세션이 재료·단계 결과를 연결합니다.
- 적·타워·유닛은 정의 ID와 실행 상태, 기능별 갱신 함수로 시작합니다.
- 유닛·현재 HP·점유 슬롯은 웨이브 사이 유지하고 슬롯 상한은 판 안에서 성장할 수 있게 구분합니다.
- 규칙은 ThorVG·브라우저 없이 검증하고, 화면 정보와 렌더러는 별도로 둡니다.
- 피해·굴착 완료·보상은 게임 시간이, Lottie는 표현이 담당합니다.
- 명령은 검증 후 적용하고 확정 결과만 HUD·음향·효과로 전달합니다.

Unity·Unreal·Godot에서 참고할 것은 이 경계를 설명하는 원리입니다. 공통 Actor·Node·Component 베이스, DI 컨테이너, 전역 이벤트 버스가 깔끔함의 전제는 아닙니다. 구체 구조와 도입 비용은 [아키텍처](architecture.md)에 있습니다.

## 실제 구현까지의 순서와 통과 조건

| 단계 | 해야 할 일 | 다음 단계의 근거 |
| --- | --- | --- |
| P0-선택 | 먼저 답할 규칙·환경과 첫 범위 검토 | 선택값·예외·남은 질문을 기록 |
| P0-수치 | 보드·굴착 경로·수확량·레시피·카드 비용·웨이브 표 작성 | 2정비 안에 도구·장갑 전략이 모두 검증 가능 |
| P1 | 승인한 파일 범위에서 규칙·좌표 테스트와 최소 WASM 실행 연결 | headless 테스트와 브라우저 smoke 확인 |
| P2 | 카드·저지·채굴·제작·보상을 3웨이브로 연결 | 서로 다른 투자·배치 결과와 종료·재시작 관찰 |
| P3 | 실제 Lottie·백엔드·해상도 비교 | 비용 분리·프레임 시간·메모리·입력 결과 |
| P4 | 결과에 따라 전체판과 성장·저장 범위 선정 | 처음부터 최종 공세까지 실제 플레이 |
| P5 | 공식 스플래시·음향·Credits·Pages·제출 점검 | 실제 배포 하위 경로에서 시작·종료·재시작 |

P0-수치에서 반드시 증명할 것은 다음과 같습니다.

1. 첫 정비 예산 안에 현재 도구로 다음 도구의 재료를 얻을 수 있습니다.
2. 다음 정비에서 상위 재료와 그 재료의 방어 용도에 접근할 수 있습니다.
3. 즉시 장갑 투자도 다음 공세에서 의미가 있고 어느 경로도 자동으로 항상 우월하지 않습니다. 금 탐색·슬롯·모집·선택 치료도 같은 굴착 예산과 경제에 연결해 다시 계산합니다.
4. 보상을 넘기거나 덱을 바꿔도 사용할 대상 없는 전용 제작을 강제하지 않습니다.
5. 첫 손패·막힌 카드·최종 강화 상한에서도 진행 수단이 있습니다.

[첫 채굴 보드·경제 초안](first-board-economy.md)에 배치·가격과 네 예시 경로를 만들고 문서 계산으로 접근·등급·굴착 수·지불 가능·재고를 검사했습니다. 실제 플레이 정보·전투 균형·게임 구현 테스트는 아직 검증하지 않았습니다. 조사 문서가 경제의 실증을 대신하지 않습니다. 성능 목표와 적 부하 단계도 지원 보장 수량과 구분합니다.

## 문서 검토 후 첫 구현 요청의 형식

다음 요청에는 선택한 규칙, 생성·변경 파일, 선정한 도구 버전·의존성, 실행할 테스트, 화면에서 확인할 결과를 함께 제시합니다. 구현 승인을 받으면 해당 범위 안에서 진행하고, 새 요구로 범위가 달라지면 변경분을 설명합니다.

타입·함수 및 인터페이스 문서 주석·의미 있는 테스트를 작성합니다. 커밋을 만드는 작업은 영어 Conventional Commits 형식을 따릅니다. 현재 기획 폴더는 Git 저장소가 아니며 이번 조사에서 저장소를 초기화하거나 커밋하지 않았습니다.

## 검증과 참고 자료

현재 문서는 프로젝트 루트에서 `python3 -m unittest discover -s tests -p 'test_*.py' -v`로 검사합니다. 게임 구현 단계의 회귀 사례와 성능 실험은 [검증 계획](validation-plan.md)을 따릅니다.

행사 일정·등록 상태는 [등록 및 제출](../registration.md)에 확인 당시 기준으로 남아 있습니다. 이번 작업은 게임·아키텍처 조사이며 행사 공지와 원격 이슈를 재확인하거나 수정한 작업은 아닙니다.
