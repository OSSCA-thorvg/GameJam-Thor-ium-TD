# 기술 계획

이 문서는 구현 후보와 검증 순서를 설명합니다. 현재 게임 구현이나 성능 측정이 완료된 상태를 의미하지 않습니다. 규칙의 확정 상태는 [결정 문서](decisions.md)를 따릅니다.

예정 폴더, 상태 소유권, 입력·시간·빌드 타깃의 구체적 제안은 [코드 구조 문서](architecture.md)를 참고합니다.

2026-11-03 [Rubiks·공식 엔진 조사](architecture-research.md)를 반영했습니다. 범용 엔진의 자산·개체·scene 체계를 복제하지 않고 현재 게임의 책임·수명·headless 테스트로 필요한 경계를 판단합니다. 개발 전 선택은 [시작 계획](preproduction-plan.md)과 [규칙 선택지](rule-options.md)에서 확인합니다.

## 실행 구조 후보

Windows·macOS 실행과 터치·UI 공유를 위한 [SDL3·공통 UI 검토안](cross-platform-ui-proposal.md)을 추가했습니다. 이를 채택하면 아래 웹 HUD 중심 역할은 공통 C++ 게임 UI와 얇은 웹 호스트로 바뀝니다. SDL 버전·빌드·UI 범위는 아직 확정하지 않았습니다.

기존 ThorVG Rubiks와 같이 **C++ 게임 코어와 ThorVG를 함께 WASM으로 빌드**하는 방식을 우선 검증합니다. 웹은 입력·페이지 수명·HUD를 담당하고, 게임 코어는 이동·표적 탐색·충돌·자원·성장을 처리하는 구상입니다.

WebCanvas도 내부에 ThorVG WASM을 사용합니다. 따라서 비교 대상은 WASM 사용 여부가 아니라 게임 계산의 위치, 앱의 JS↔WASM 호출 방식, 렌더링 백엔드와 화면 출력 방식입니다. 커스텀 WASM의 우위는 동일 장면을 측정하기 전에는 확정하지 않습니다. [ThorVG Web](https://github.com/thorvg/thorvg.web), [Emscripten 지침](https://emscripten.org/docs/compiling/best_practices.html)

## 책임 분리

| 영역 | 책임 | 경계 |
| --- | --- | --- |
| 게임 규칙 | 웨이브, 전투, 카드, 자원, 채굴, 성장 상태 | ThorVG와 브라우저 없이 테스트 가능하게 구성 |
| 표현 상태 | 논리 좌표를 화면 좌표로 변환, 연출 상태와 애니메이션 선택 | 피해·보상 판정을 결정하지 않음 |
| ThorVG 렌더러 | 도형·Lottie·이미지 합성과 그리기 | 렌더러 교체가 게임 규칙에 영향을 주지 않도록 구성 |
| WASM 경계 | 입력 묶음, 프레임 진행, 필요한 상태 조회 | 개체마다 JS에서 호출하는 형태를 줄임 |
| 웹 셸 | 로딩, HUD, 포인터 입력, 리사이즈, 탭 전환 | 게임 상태의 중복 소유를 피함 |

모듈의 세부 폴더·클래스·ABI는 구현 범위를 승인받은 뒤 정합니다. 소유권과 수명, 좌표 단위, 시간 단위는 인터페이스에 명시합니다.

첫 연결판의 작업 단위는 [프로토타입 상세안](prototype-plan.md)의 P0~P5를 따릅니다. 규칙의 승인과 구현 작업의 승인을 구분하고, 수치·카드·공세·룬 정의는 변경 가능하게 분리하되 필요한 데이터 형식은 첫 구현 범위를 정할 때 선택합니다.

2026-11-03 검토한 로컬 프로젝트는 `ThorVG/활동/해커톤/thorvg-rubiks`의 HEAD `6238cff2cc8937eb123f93513aef329a49fe2345`입니다. 추적 파일 수정은 없었고 미추적 `.claude/`만 있었습니다. 다음 경로는 참고 프로젝트 내부 경로이며 새 프로젝트의 구현 파일이 아닙니다.

Rubiks의 코어 수명 관리·테스트 경계를 참고하되 큐브 도메인과 전용 UI를 게임 규칙에 가져오지 않습니다. 현재 로더 설정을 그대로 복사하면 Lottie 활용 계획과 맞지 않는다는 점을 먼저 확인해야 합니다.

이전의 ‘매 프레임 재구성’ 요약을 위 조건으로 정정했습니다. Rubiks의 다중 surface API·큐브 3D picking·애니메이션 완료에 맞춘 논리 회전은 이 게임의 scene·입력·전투 시간 구조로 그대로 가져오지 않습니다.

## 지형과 좌표

최신 시각 방향은 캐주얼한 2D입니다. 지층의 단면과 공간 연결은 유지하되 깊이는 단순한 레이어·옆면·그림자로 표현하는 방향으로 기획합니다.

Q-22=A에 따라 지상 탑다운·지하 단면을 단계별로 전환합니다. Q-03=A의 전투·정비 분리·정비당 5굴착·추리 시간 제한 없음도 선택했습니다. Q-19=B의 반복 소환은 카드 한 장과 여러 유닛 상태의 관계를 허용하고 전장 전체 슬롯을 검증하는 구조로 반영합니다.

Q-19 후속 선택은 기본 6슬롯·첫 유닛당 1슬롯·금 재화 상한 강화·지정 위치 저지·생존 HP 유지·정비 재료 치료·무료 재배치입니다. UnitState와 슬롯 성장은 한 판의 상태이며 웨이브 재생성 대상이 아닙니다. 강화·치료·재배치는 각각 비용·대상·위치를 검증합니다. 금 잔액은 제작 재고와 구분하는 안이며 Q-23=A로 유닛 카드 후보 3개 중 1개 획득을 선택했습니다. 금 모집과 실제 카드 소환의 에너지·슬롯 처리는 분리합니다. 자세한 정의는 [경제안](economy-plan.md)을 따릅니다.

지하 논리 좌표는 수평 위치와 지층 깊이를 가진 격자로 관리하는 안입니다. Q-04=A로 열린 갱도 상하좌우 자동 이동부터 시작하고 중력·사다리는 후속 전환 방향으로 둡니다. 단면의 윗면·옆면 두께는 표현 계층에서 계산합니다. Q-08=A의 숫자는 최초 둥지 배치의 주변 8칸 수로 고정하며 채굴 여부·광석·둥지 처리 상태와 공개 정보를 구분합니다.

지상 방어·지하 채굴 연결과 타일 지정 후 자동 이동·굴착을 선택했습니다. Q-01=A로 지상 확장은 정해진 웨이브 뒤 열고 지하 깊이·유적을 필수 조건으로 두지 않습니다. 첫 전장은 고정 적 경로·배치 칸을 사용하며 지상 좌표와 지하 깊이를 구분합니다. 이후 자유 배치·경로 재계산으로 전환할 지형·점유·설치·경로 계산의 경계는 [아키텍처](architecture.md)에 제안합니다. 사거리·충돌은 논리 좌표에서 계산하고 화면 투영과 카메라 이동으로 판정이 바뀌지 않게 합니다. 카드를 끌 때 설치 후보와 사거리를 표시하고, 카메라 이동과 드래그가 충돌하지 않는 입력 규칙을 정합니다.

광부의 이동 중 상태와 굴착 완료 처리를 분리해 중복 입력·정비 종료·화면 전환으로 자원과 작업 횟수가 이중 반영되지 않게 합니다. 지하에서 예약한 추가 공세는 다음 전투의 편성에 한 번만 반영하는 규칙 제안입니다.

## Lottie 활용

ThorVG Animation이 프레임을 제어하고 해당 Picture를 게임 캔버스에 합성하는 방식이 후보입니다. 개체의 상태와 경과 시간에서 이동·사망 구간을 선택하며 피해 판정과 보상은 게임 규칙이 소유합니다. [공식 Animation API](https://github.com/thorvg/thorvg/blob/main/inc/thorvg.h), [다중 Lottie 예제](https://github.com/thorvg/thorvg.example/blob/main/src/Lottie.cpp)

- 일반 적의 단순한 이동 루프와 사망 연출부터 측정합니다.
- 인스턴스 생성·회수, 에셋 로딩, 프레임 갱신 비용을 구분합니다. 같은 파일이라는 이유로 모든 내부 상태가 자동 공유된다고 가정하지 않습니다.
- 개체마다 시작 시점을 달리하고 상태 이상과 이동 속도를 게임 시간에 맞춰 반영합니다.
- 레이어·경로·마스크·합성 효과의 복잡도를 에셋 기준에 포함합니다.
- 위치 갱신과 애니메이션 갱신 빈도를 나누는 안, 프레임 캐시 활용은 측정 결과에 따라 검토합니다. 캐시는 메모리·화질·배포 크기도 함께 비교합니다.

## 성능과 배포

CPU 렌더링과 WebGL을 동일한 장면·해상도에서 비교합니다. WebGPU는 목표 환경과 도입 비용을 확인한 뒤 판단합니다. Q-07 답변으로 데스크톱 60 FPS 검증을 우선하고 모바일 UI·UX도 준비합니다. 실제 기준 기기·브라우저·해상도·DPR과 모바일 성능 기준은 미정이며 [검증 계획](validation-plan.md)의 환경표에 기록합니다. 모바일 화면·터치·안전 영역·조작 취소는 [UI·UX 계획](interface-plan.md)에 정리했습니다.

GitHub Pages의 프로젝트 하위 경로에서도 WASM·Lottie·폰트가 로딩되어야 합니다. 게임 시작 시 공식 ThorVG 스플래시를 타이틀보다 먼저 ThorVG로 재생하고, 새로고침·리사이즈·탭 복귀를 검증합니다. 자세한 행사 기준은 [등록 및 제출](../registration.md)을 따릅니다.

## 개발 규칙

- 사용자 지침에 따라 타입을 명시하고 함수·클래스·공개 인터페이스에 docstring 또는 언어에 맞는 문서 주석을 작성합니다.
- 게임 규칙을 검증하는 테스트 코드를 작성하고 변경에 맞는 테스트를 실행합니다.
- 구현 전에 구체적인 변경 범위와 설계를 제시하고 사용자 승인을 받습니다. 이미 승인된 범위에서는 불필요하게 재확인하지 않습니다.
- 커밋을 작성할 때는 영어 Conventional Commits 형식을 사용하고 변경 이유와 검증 내용을 구체적으로 설명합니다.
- 도구·의존성 버전은 검증 후 고정합니다. 아직 선정하지 않은 버전을 문서에서 확정된 것으로 다루지 않습니다.
