# 후반 웨이브 프레임 예산

2026-11-13. 5구역 16웨이브처럼 적이 200마리 넘게 동시에 살아 있는 장면에서 웹 프레임 시간을 쟀고, 한 프레임의 p95를 16.7ms 아래로 맞췄다. 개체 애니메이션의 공유 프레임은 [공유 프레임·물량 측정](shared-animation-cache.md), 프레임 구간별 시간 기록은 [아키텍처 검토 후속](architecture-follow-up.md)의 ‘전체 출력 경로와 측정’에 있다.

## 측정 장면

- `?bench=s<구역>w<웨이브>`를 붙여 열면 strong 봇([Autoplayer.h](../src/game/autoplay/Autoplayer.h))이 실제 명령으로 그 웨이브 직전까지 진행한 판에서 전투가 바로 시작된다. `&crowd=1.5`는 그 웨이브부터 출현 수를 곱하고 기지 체력을 올린다. `&anim=vector|cache`는 그 세션의 애니메이션 방식을 고른다. 네이티브는 `--bench=s5w16 --crowd=1.5`처럼 준다.
- 측정 세션은 저장을 쓰지 않는다. 전투 중 봇이 0.5초마다 카드를 낸다.
- WASM의 `thorium_bench_frames`가 전투 프레임마다 생존 적 수와 단계별 CPU 시간을 돌려준다. 브라우저 `peak.js`는 이 경로가 동작하고 적 150마리 이상이 기록되는지 확인한다. 기기마다 시간이 달라 프레임 예산 자체는 테스트 기준에 넣지 않았다.

## 적용한 것

| 항목 | 내용 |
| --- | --- |
| 배경 보관 | 화면 배경, 전장 틀, 바닥 채움을 한 번 그린 픽셀로 보관하고 프레임마다 복사한다(`Renderer::backdrop`). 불투명 배경 위에서는 마지막 알파 변환을 생략한다 |
| 지형 레이어 | 바닥 무늬·길·기믹 지형을 `Renderer::cachedLayer`로 보관한다. 카메라·경로·패드·바위가 바뀌면 다시 그리고, 화면 흔들림은 보관한 그림을 정수 픽셀만큼 옮긴다 |
| 화면 밖 생략 | 전장 틀 밖의 적·건물·유닛·패드·전투 연출·표식을 장면에 넣지 않는다 |
| 적응형 렌더 배율 | 최근 프레임의 CPU 작업이 13.5ms를 넘으면 렌더 픽셀 밀도를 1 → 0.85 → 0.7배로 내리고, 8.5ms 아래로 내려가면 한 단계씩 올린다([RenderScale.h](../src/engine/render/RenderScale.h)). 논리 픽셀당 물리 픽셀 1 아래로는 내려가지 않는다 |

## 결과

헤드리스 Chromium, 1280×800, 5구역 16웨이브, 적 200마리 이상인 프레임의 전체 시간이다. `crowd=1.5` 줄은 300마리 이상인 프레임이다. 아래 표는 [구역별 전장 기믹](stage-gimmicks.md)을 넣기 전에 쟀다.

| 조건 | p50 | p95 |
| --- | --- | --- |
| 배율 1 화면 · 벡터 원본 | 12.5 | 13.5 |
| 배율 1 화면 · 공유 프레임 | 9.6 | 10.3 |
| 배율 1 화면 · 벡터 · crowd 1.5 (최대 360마리) | 12.7 | 14.1 |
| 배율 2 화면 · 벡터 · 적응형 배율 전 | 16.0 | 18.2 |
| 배율 2 화면 · 공유 프레임 · 적응형 배율 전 | 15.2 | 16.6 |
| 배율 2 화면 · 벡터 · 적응형 배율 후 | 12.2 | 13.4 |
| 배율 2 화면 · 벡터 · crowd 1.5 · 적응형 배율 후 | 16.9 | 18.3 |

기믹을 넣은 최종 빌드를 두 번 잰 p95는 배율 1 화면 12.8·15.5ms, 배율 2 화면(적응형 배율) 13.8·16.7ms였다. 두 번의 차이는 같은 기기의 다른 작업 부하에서 왔다.

실제 5구역 후반(최대 227마리)은 두 화면 배율 모두 16.7ms 안이다. 출현 수를 1.5배로 늘린 360마리 장면은 배율 2 화면에서 18.3ms로 넘는다.

네이티브 샘플링에서는 도형 채우기와 윤곽 생성이 시간의 대부분이었다. 화면 요소를 하나씩 끄고 잰 래스터 시간(1800×1200, 360마리, 평균 9.4ms, 판마다 ±1ms)은 전장 4.3ms, 손패 1.3ms, 정비·명령 패널 0.6ms, 상단 HUD 0.3ms였다.

## 한계

- 측정하는 동안 같은 기기에서 다른 빌드와 가상 머신이 돌고 있었다. 수치는 조건끼리의 비교로 읽는다.
- 측정 장면이 이 변경과 함께 들어와, 변경 전 코드를 같은 장면에서 재지 않았다.
- 실제 모바일 기기와 실제 브라우저 창에서는 재지 않았다.
- 적응형 배율은 부하가 높은 동안 화면이 조금 흐려진다. 설정으로 끌 수 없다.
